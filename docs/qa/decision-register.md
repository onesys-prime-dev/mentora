## 0. How to use this register

### 0.1 The three categories used in all three planning documents

| Category | Short | Meaning | Allowed to base a test's expected result on it? |
|---|---|---|---|
| **Verified current implementation behavior** | **VCI** | What the code does today, established by reading it (marked **[V]** when I checked it directly, **[A]** when an audit agent read it). Nothing has been run. | Only as a `Draft` characterization, never as a requirement. A VCI behavior that contradicts an authoritative requirement is a **defect**, not an expectation. |
| **Intended behavior established by an authoritative requirement** | **IBR** | What the product should do, according to (1) a numbered decision in `docs/audit-2026-10-23-decisions.md` (decisions 1.1–16.1, U1–U5, D1–D11; **provisional until PLN-01 records who approved it**), (2) a catalog case marked `Confirmed by Shuay` (all 17 P1 cases, 6–7 Oct 2026), or (3) a decision the reviewer recorded in Part F of this register (cited in the matrix as `SO:<id>`). | Yes. |
| **Unresolved behavior requiring a decision** | **UNR** | Behavior where no authoritative requirement says what is right, or where sources disagree. | **No.** Scenarios depending on it are `BLK` (blocked) until the decision is recorded here. |

Documents under `docs/` that describe how a feature works (for example `roles-and-permissions.md`, `sis-integration.md`) are **documented design**, not authority: they are used as evidence of intent and checked against the code, but a conflict with the code is recorded as a contradiction (Part B), not resolved in their favor.

### 0.2 Status values used in this register

| Status | Meaning |
|---|---|
| **UNRESOLVED** | A product or owner decision is needed. Dependent scenarios are blocked. |
| **PARTLY** | An authoritative decision answers part of it. The remainder needs a decision. |
| **RESOLVED-IBR** | An authoritative requirement already answers it. It is not a question: the scenario is written from the requirement and, where the code differs, it is a regression test for a defect. |
| **VERIFY** | A runtime fact, not a product decision. Someone must run or inspect it. |
| **DECIDED** | Recorded in Part F. The dependent scenarios are released in the coverage matrix. |
| **DECIDED-OPEN** | Decided, but the entry names or leaves a sub-point undefined, conditional or "proposed". Only the decided part is an oracle. |
| **OPEN** | Not decided: the entry restates the question, gives no names or dates, or leaves the value provisional. Dependent scenarios stay blocked or provisional. |

### 0.3 Columns

- **Question**: the inventory's wording, with the **verified current behavior (VCI)** appended where useful.
- **Affected modules**: coverage-matrix module codes.
- **Why it matters to testing**: what a tester cannot write or judge without the answer.
- **Decision or clarification needed**: the exact thing to settle. Wording is deliberately a question, not a proposal.
- **Scenarios affected**: backlog scenarios (`PS-…`) in the coverage matrix that mention this item, generated from the backlog so the two documents cannot drift.

### 0.4 Reviewer's record

The reviewer wrote the decision, name and date in Part F. This register now shows the resulting status on every row (the old status is kept in brackets). Part G lists the follow-ups. A blocked scenario was released only where a row is `DECIDED` or `DECIDED-OPEN`.
