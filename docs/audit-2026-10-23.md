# Mentora audit — 2026-10-23

An audit only: no code was changed. Findings are numbered so they can be referred to ("fix 2 and 5").

**What this repo does:** Mentora is a learning management system (LMS) for schools and universities, built on CodeIgniter 4. Seven roles share one app: system admin, institution admin, dean, chairperson, instructor, student and parent. It covers course content, quizzes and assignments, grading, grade approvals, a student information system (SIS) sync and an AI question builder.

**Load assumed:** a few institutions, each with hundreds to a few thousand students using it at the same time. A cron and a background worker run beside the website.

## How it was checked

- **Routes:** a script checked that all 662 routes in `app/Config/Routes.php` reach a real controller method with matching arguments.
- **Code read:** every access filter, plus the services behind the risky flows: grades, approvals, files, quizzes, view-as, export, backup, purge, tokens and permissions.
- **PHPUnit:** 7,138 tests, 7,132 pass. All 6 failures are in one fragile test (finding 14).
- **JavaScript (Vitest):** 374 tests, 373 pass. The one failure (`tests/js/pages/calendar-read-only.test.js`) was a 5-second timeout while PHPUnit ran at the same time, and it passes when run alone.

Status key used below: ✅ works (route, controller and service read; tests pass) · ⚠️ partial or not connected · ❌ missing

## Findings (most important first)

### Must fix

**1. Grade-override requests in a department with no dean are stuck forever**
- **What this is:** An instructor asks to change a final grade. The request goes to the chairperson, then the dean. If the department has no dean, it goes to `awaiting_institution` (`app/Services/Courses/Grades/OverrideRequestChain.php:49-52`).
- **Problem:** Nothing reads that status. No route, screen or notification lets the institution admin decide it. The dean can only decide `awaiting_dean` (`GradeOverrideRequestService.php:662`). Deactivating a dean, or removing their dean role, moves all their open requests into this dead end (`app/Services/Users/UserAdminService.php:195, 309`; `GradeOverrideRequestService::retargetDepartment`, line 490).
- **If we skip it:** Those grade changes never happen. The requester can only withdraw.

**2. Departments with no dean never send grades to the SIS**
- **What this is:** "Does this institution have a dean?" is answered for the whole institution (`GradeOverrideRequestService.php:39-52`, reused by `GradeSignoffService::appliesTo`). The SIS export then sends only grades a dean signed off (`app/Services/Sis/SisGradeExporter.php:199-213, 240`).
- **Problem:** Say department A has a dean and department B has none. B's grades can never be signed off, because only the dean of B could do it. So they are skipped as "not signed off" on every run.
- **If we skip it:** A whole department's final grades never reach the SIS, and nothing reports why.

**3. "View as" a student uses up the student's real quiz attempt**
- **What this is:** View-as is meant to be view-only. It blocks every request except reads (GET) (`app/Filters/ImpersonationFilter.php:54-56`).
- **Problem:** Opening a quiz is a GET (`Routes.php:104`), but it creates a new "In Progress" attempt and starts the timer (`app/Services/Courses/Assessments/QuizAttemptService.php:100-106`). An admin who opens a 1-attempt quiz while viewing as a student uses up that student's only attempt. No test covers this.
- **If we skip it:** Students lose attempts because of a support check.

**4. CSRF protection has never been switched on**
- **What this is:** CSRF is an attack where another page makes your browser submit a form while you are signed in. A CSRF token stops it.
- **Problem:** The `csrf` filter is commented out in `app/Config/Filters.php:109` and has been since the first commit (`1364dc3`). Forms render a token, but nothing checks it. The only protection is `SameSite=Lax` cookies (`app/Config/Cookie.php:90`), which do not stop a page on a sibling subdomain. The one test that "checks" the token appends the expected string to the HTML it searches, so it can never fail (`tests/unit/ComponentViewsTest.php:240`).
- **If we skip it:** Any same-site page can trigger posts like removing a person or a grade change for a signed-in user.

**5. Dean and institution admin get an error page on a lesson's direct link**
- **What this is:** `dean/courses/{id}/{slug}/modules/items/{item}` and the matching institution route (`Routes.php:369, 747`) pass the URL arguments `$1/$2/$3`.
- **Problem:** The handler takes `(int $offeringId, int $learningItemId)` (`app/Controllers/Courses/ModuleController.php:46-49`), so it receives the slug (for example `intro-cs`) as the item id. That throws a TypeError (HTTP 500). Even if it worked, it returns JSON, not a page. Students, instructors and chairpersons go through `CourseController::view` and are fine.
- **If we skip it:** Reloading or sharing a lesson link breaks for those two roles.

**6. Scheduled jobs are not installed, so several features never run**
- **What this is:** Several features depend on cron jobs. `docs/server-setup.md:148-151` says neither server has them yet. The servers themselves were not checked.
- **Problem:** Read-only mode is driven only by the stored status, which only `subscriptions:sync` changes (`app/Services/Institutions/InstitutionAccess.php:56-59`). Without the cron:
  - an expired subscription keeps full write access;
  - the app takes no backups;
  - parents get no change emails;
  - SIS runs and deleted-institution purges never happen.
- **If we skip it:** Unpaid institutions keep working, and there are no app backups.

**7. The Roles page has permissions that change nothing**
- **What this is:** The admin can toggle any permission for any role (`app/Controllers/Admin/RolesController.php`). This is stored and loaded into `app/Config/AuthGroups.php`.
- **Problem:** Nine permissions are never checked anywhere: `grades.approve`, `grades.signoff`, `courses.manage`, `grading.manage`, `announcements.manage`, `program.monitor`, `followups.manage`, `audit.manage` and `monitoring.manage`. A grep of the routes and code finds zero uses. The dean's approval and sign-off routes check only `role:dean` (`Routes.php:322-331`).
- **If we skip it:** An admin turns off "Approve final-grade overrides" for deans, the screen says it's off, and deans can still approve.

### Should fix

**8. Belonging to two institutions overrides read-only**
- **Problem:** If any one of a person's institutions is writable, they can write everywhere (`InstitutionAccess.php:63-65`). An instructor at institution A (active) and B (expired) can still edit B's courses.
- **If we skip it:** Read-only mode does not hold for people with more than one membership.

**9. The instructor group skips the quiz rules even when acting as a student**
- **Problem:** Quiz start checks `$user->inGroup('instructor')`, not the role the person is acting as (`QuizAttemptService.php:48, 70`). Someone who teaches one course and studies in another can open an unpublished quiz, or start one after it closes, in the course where they are a student.
- **If we skip it:** Quiz windows and hidden quizzes leak to these people.

**10. Purging an institution keeps every uploaded file**
- **Problem:** Purge deletes only the institution row, and the database cascades the rest (`app/Services/Institutions/InstitutionService.php:290`). Files belong to users, not institutions (`app/Database/Migrations/*CreateFilesTable.php:72-78`), and users are kept on purpose (`InstitutionService.php:245-247`). So student work, videos and PDFs stay in the `files` table and on disk.
- **If we skip it:** "Permanently removed" data is still stored, which is a privacy and retention problem.

**11. A broken backup is recorded as good**
- **Problem:** The results of `gzwrite` are never checked (`app/Services/Backup/MysqldumpRunner.php:52-54`). With a full disk, the dump still exits 0 and a truncated file is kept as a successful backup. Errors are also read only after all the output, so a large error stream could hang the job.
- **If we skip it:** You find out the backup is broken on the day you need it.

**12. The institution data export can run out of memory**
- **Problem:** The code comment says the rows are a generator, but each query is fully loaded with `getResultArray()` first (`app/Services/Institutions/InstitutionExport.php:201-205`). This happens inside the web request (`app/Controllers/Institution/ExportController.php:53`). `submissions.csv` for a big institution (thousands of students × dozens of assessments) holds hundreds of thousands of rows in memory.
- **If we skip it:** Large institutions get "The export could not be made", and this is the one export they are entitled to after their subscription ends.

**13. Class schedules have no way to be entered**
- **Problem:** Nothing writes `course_schedules` except `app/Database/Seeds/CourseSchedulesSeeder.php` and the term-copy service (`OfferingCopyService`). The Schedule page, class times on the calendar and the teaching-load panel read it, but no admin form, offering form or SIS import fills it.
- **If we skip it:** A real institution never sees a schedule.

**14. The AI worker endpoint test fails on any machine with the secret set**
- **Problem:** `tests/feature/AiWorkerEndpointsTest.php` sets the secret only in `$_SERVER`. CodeIgniter's `env()` reads `$_ENV` first, which is filled from `.env`. So all 6 tests in that file fail locally (401 instead of 503/200/422) and pass only where no secret is set.
- **If we skip it:** Developers learn to ignore red tests.

### Nice to have

**15. Opening a quiz in two tabs at the same moment** gives the second tab an unhandled duplicate-key database error. The unique key added in migration `2026-11-10-000001_AddUniqueSubmissionAttempt.php` stops the attempt-limit bypass, but `QuizAttemptService.php:100-110` doesn't catch the error.

**16. Chairperson endorse and send-back are not atomic, unlike the dean's decision** (`GradeOverrideRequestService.php:210-282` vs `claim` at line 677). If two chairs act at once, both writes land, the last one wins, and both notifications go out.

### Shared across roles (all checked, all fine)
- Invitation and reset links: hashed, expiring, used once, with an atomic update (`PasswordResetService.php:129, 188-191`; `InvitationService.php:324`).
- Role switching allows only roles you hold (`app/Services/Auth/ActiveRoleService.php:56-65`).
- Every file goes through `app/Services/Storage/FileAccessService.php`.
- The AI worker API is loopback-only and checks its secret with a constant-time compare (`app/Filters/AiWorkerFilter.php:22-33`).
- Rich text is escaped (`app/Helpers/announcement_helper.php:110`).
- Notifications are deduplicated by a unique key `(user_id, dedupe_key)`.
- Sign-in lockout is per email (`app/Filters/LoginLockoutFilter.php`).
